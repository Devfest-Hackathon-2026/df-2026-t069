# Firestore読み書き量の内訳（#12・#17）

確認日：2026-11-09。実請求の計測ではなく、コードの呼出回数と返却文書数に基づく見積り。

## 前提・確認対象

- 月100通話。
- 主ケースは1通話でGemini分析60回、その全結果60件を検知レポートとして1件ずつ保存。
- セッション作成1回、終了1回、終了後レポート取得1回。
- 分析対象バッチがそろったときだけ/analyzeへ送り、Firestoreの確認は60回。
- 分析状態は現在の「1通話1ドキュメント」版。1ID1ドキュメント版の以前の概算は適用しない。
- 保存処理は取得済み `origin/feature/#17-issue-2026118` のコミット919bc70を確認。
- トランザクション競合・通信再試行・追加の画面閲覧・管理コンソール操作・削除等は別。
- 画像リンクは取得できなかったため、共有された文章の前提とコードで算出。

60「発言」と60「分析バッチ」は異なる。現在の仕様では初回も以降も新しい5発言ごとに分析するため、
60発言では12バッチ（5、10、15、…、60件目）。5件未満の端数を通話終了時に分析する処理は未実装。
60バッチの成功には、通常の逐次受信なら300発言が必要。

## なぜ検知追加の読み取りが増えるか

保存処理は `SessionService.record_detection` → `FirestoreSessionStore.add_detection`。

i件目を追加するとき：

1. サービス側のget_session：セッション1＋既存検知max(i−1, 1)読み取り。
2. add_detectionの存在確認：セッション1読み取り。
3. セッション集計と新規検知：2書き込み。
4. add_detectionが返すget_session：セッション1＋追加後の検知i読み取り。

したがってi件目の読み取りは `3 + max(i−1, 1) + i`。
空の一覧クエリにも最低1読み取りが課金されるため、最初は5読み取り。
D件を順に追加すると、D>=1で `D² + 3D + 1` 読み取り・`2D`書き込み。
60件では3781読み取りとなる。保存件数が2倍になったとき、追加部分の読み取りは約4倍に増える。

## 保存する件数による違い

分析回数は60回のまま、レポートへ保存する件数Dだけを変えた場合。

| 保存D件／通話 | 読取／通話 | 書込／通話 | 読取／100通話 | 書込／100通話 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 125 | 122 | 12,500 | 12,200 |
| 10 | 274 | 142 | 27,400 | 14,200 |
| 60 | 4,024 | 242 | 402,400 | 24,200 |

分析結果がlowなら不審項目として保存しない方針などにより、Dは分析回数より少なくなり得る。
保存方針は保存・UI担当者と確定する。分析バッチ数と保存件数を同一視しない。

## 一般式

- A：分析して予約・完了処理を行う回数。
- P：件数条件を満たしFirestoreに予約・重複確認を行う回数（待機分も含む）。
- D：検知レポートに1件ずつ追加保存する件数。
- V：通話終了後にレポートを取得する回数。

```text
分析状態の読み取り = P + A
分析状態の書き込み = 2A

セッション開始 = 0読取・1書込
セッション終了 = 2 + max(D, 1) 読取・1書込
レポート表示 = V × (1 + max(D, 1)) 読取
検知追加 = Σ[i=1..D] (3 + max(i−1, 1) + i) 読取・2D書込
```

同じバッチの再送はFirestoreの確認読み取りを増やすが、分析済みならGeminiは呼ばず書き込まない。
発言ごとに送信する場合、60発言ならP=56（1〜4件時はDBアクセスなし）、A=12。
このとき分析状態だけで68読み取り・24書き込み。バッチ成立時だけ送るならP=A=12で24読み取りまで減る。

## 無料枠は日次

Standardの無料枠は1日50,000文書読取・20,000文書書込。無料DBはプロジェクトにつき1つ。
月の合計で無料／有料を決めず、太平洋時間での日次使用量を確認する。

主ケース（4024読取・242書込／通話）を30日に分散すれば1日平均約13,413読取・807書込。
1日3〜4通話なら約12,072〜16,096読取、726〜968書込。

同じ100通話を1日に集中すると、他の利用がない場合でも無料枠超過は352,400読取・4,200書込。
主ケースでは1日12通話で48,288読取、13通話で52,312読取となり、読み取りが先に無料枠を超える。
超過しただけで高額になるとは断定せず、選択したリージョンの超過単価を掛けて請求額を見積もる。

これらは読み書きの検討であり、保存容量・インデックス容量・ネットワーク転送・TTL削除・
バックアップ・Gemini・Cloud Run・文字起こし等の費用を含まない。
TTL削除は無料枠外。通常削除・TTL・保持期限の具体的運用は別途決める。

## 削減するなら優先する箇所

1. 検知の追加保存時、全検知一覧を保存前後に読み直さない。存在確認・集計更新・追加文書の返却だけにする。
2. 一覧は終了後のレポート表示時に取得し、再表示やポーリングの回数を把握する。
3. 発言収集側でもバッチ成立時にのみ/analyzeを呼び、待機用のFirestore確認を減らす。
4. 実測でP・A・D・V、トランザクション再試行、日次のFirestore使用量を記録する。

保存APIの返却形式変更は既存UIと調整が必要。この見積りでは保存コードを変更していない。

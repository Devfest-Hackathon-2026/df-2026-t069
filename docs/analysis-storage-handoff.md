# 発言分析と検知結果保存の連携方針（#12・#13・#17）

更新日：2026-11-10。今回の実装範囲、保存担当者との調整事項、読み書き量を共有するためのメモ。

## 追加決定：固定スコアと検知時刻

以下は本セッションで決定した仕様で、本文中のスコア・時刻の未確定記述に優先する。

| 分析結果 | 固定スコア | 保存用判定 |
| --- | ---: | --- |
| low・注意の根拠あり | 0.25 | low（軽い注意として保存） |
| low・根拠なし | — | 保存しない |
| medium | 0.5 | suspicious |
| high | 0.85 | likely_fake |

スコアは確率ではなく、既存の0.4/0.7の判定境界に合わせた危険度区分の値。
`app/services/analysis_detection_mapper.py` の `to_detection_item` で保存用データに変換する。
呼出側は実際に分析した発言群（通常は末尾5件）を渡す。
録音開始を0秒とし、引用が含まれる発言の `startSec` を `timestamp_sec` に設定する。
解析完了時刻や保存時刻は使わない。引用が発言の途中でも発言自体の開始位置を使う。
引用元がない、または複数の発言に一致する場合は `ValueError` とし、時刻を推測しない。
保存側の文字数上限は `DetectionItem` の検証に従い、超過した場合は検証エラーとなる。

`/analyze` の自動保存接続は実装済み。is_suspicious=trueならlowを含め保存し、
falseの通常会話は保存しない。公開JSONは6項目のまま、lowのtrue＋カテゴリ＋引用を許可する。
軽い注意は即時警告しない。SessionVerdictにlowを追加し、総合判定でも軽い注意を区別する。
下記の旧メモの保存未実装記述より、本節とdocs/api-contract.mdの現行仕様を優先する。

## 1. 「一覧」は2種類ある

| データ | 内容 | 主な用途 |
| --- | --- | --- |
| utterances | 文字起こしで確定した発言。id・text・startSec | 新しい5件を/analyzeへ送り、Geminiで分析 |
| detections | 不審な発言の時刻・引用・カテゴリ・理由・助言などの判定結果 | 通話終了後レポート |

検知結果の一覧を保存のたびに取り出す処理を削減しても、5発言ごとのAI分析には影響しない。
発言バッファは文字起こし・送信側が保持するものであり、過去の検知結果から発言を再構成しない。

## 2. 5件ごとの分析とID

```text
新規u1〜u5   → /analyze → 分析
新規u6〜u10  → /analyze → 分析
新規u11〜u15 → /analyze → 分析
```

- 初回も5件そろった時点で分析する。以前の「初回6件目」は廃止。
- バックエンドは受信配列の末尾5件を使用する。末尾5件に分析済み・分析中のIDがあれば204で待機。
- APIは不足分をためない。送信側で未送信の確定発言をため、5件ごとに送る接続処理は未実装。
- 送信側は失敗時に同じ5件を再送できるよう、成功確認前にバッファを捨てない。
- 同じ発言の再送は同じIDを維持する。同じ文章でも別の発言なら別ID。
- sessionIdは通話ごとに固定。utterances[].idはその通話の発言を識別する文字列。
- startSecは録音開始から発言開始までの経過秒数。文字起こし完了・API送信の時刻ではない。
- 5件未満の端数を通話終了時に分析する処理、複数バッチを取りこぼさない送信キューは後続対応。

初回から6件以上の累積配列も受信できるが、末尾5件以外は分析しない。
5件を超える発言が一度に届いた場合に全件を分析するためには、呼出側で順番に5件ずつ送る必要がある。

## 3. 現在の保存先と担当範囲

| 保存先 | 内容 | 実装元 |
| --- | --- | --- |
| analysis_states/{SHA256(sessionId)} | 分析済みIDハッシュ、分析中予約・所有者・期限、更新時刻 | 今回の#12 |
| sessions/{sessionId} | 通話の開始・終了、検知件数、最大危険度など | 保存担当者の#17 |
| sessions/{sessionId}/detections/{検知ID} | 個々の判定結果 | 保存担当者の#17 |

分析状態管理は本文を保存しない。予約と完了更新はFirestoreのトランザクションで行い、
Geminiはトランザクション外で呼び出す。成功時のみ分析済みにし、失敗時は予約解除。
ローカルSQLiteも残すが、auto設定でvertexaiを使う場合はFirestoreを選択する。

現在の/analyzeは判定結果を返すところまでで、#17の検知結果保存APIは呼び出していない。
この保存連携は後続対応とする。分析状態の保存成功は、検知レポートの保存成功を意味しない。
分析済みになった後にレポート保存だけが失敗した場合、AIを再実行せず保存だけ再試行できる設計が必要。

## 4. 保存APIの現状とJSONの対応

対象：チームのタスク#17（会話中のGitHub Issue #23／PR #48として共有されている保存実装）。
取得済みorigin/feature/#17-issue-2026118のコードを確認したもので、他メンバーの未push変更は含まない。

```text
POST /api/v1/sessions/{sessionId}/detections
```

先にセッション作成APIを呼ぶ必要がある。保存APIは1件のDetectionItemを受け取る。

| 保存側項目 | 現在の制約 | こちらから渡す情報・確認事項 |
| --- | --- | --- |
| timestamp_sec | 必須・0以上 | 対象発言のstartSec。通話開始／録音開始の基準を統一する |
| quote | 必須・1〜1000文字 | AIの引用。ただし入力に実在することを検証する |
| category | 必須・自由文字列 | C1〜C5のコードに統一する方針を確認 |
| risk_score | 必須・0〜1 | #11にはない。数値化を独断で行わず保存担当者と調整 |
| risk_level | 文字列。既定suspicious | low/medium/highと保存側集計・UIの整合を確認 |
| reason | 必須・1〜1000文字 | AIの理由。こちらは現在文字数上限なしなので制約調整も必要 |
| advice | 任意・null可・最大500文字 | AIの助言。こちらは必須・上限なしなので制約調整も必要 |
| speaker | 任意・null可 | 文字起こし側の話者情報を利用する場合に対応付ける |
| id | 省略時UUID生成 | 検知結果ID。発言IDとは別。保存再送時の重複防止方針を決める |
| created_at | 省略時生成 | 原則保存側で付与 |
| expire_at | 任意 | セッションの保存期限と合わせる。TTLの有効化・費用は別途確認 |

sessionIdはJSONではなくURLに指定する。#11の6項目を保存側へ無条件にそのまま送れるわけではない。
保存側の都合でAIへ根拠のないrisk_scoreを生成させず、確定済みの#11を基準に調整する。
medium/highを保存し、highのみ即時警告、mediumは終了後レポートという表示方針。
lowは軽い注意の根拠がある場合のみ保存し、根拠なしの通常会話は保存しない。

## 5. 対象発言・時刻の紐付けは未実装

現在、AIへ送るのは本文だけ。6項目の応答に対象発言ID・時刻はない。
入力のstartSecを流用するには、5件のうちどの発言が対象か特定する必要がある。

提案：AIへの入力に発言IDを含め、内部出力で対象IDを返させる。
バックエンドでIDと引用の対応を検証し、そのIDの入力startSecを保存用時刻へ転記する。
時刻をAIに生成させない。quoteの文字列検索だけでは、同じ文章が複数ある場合に一意に決まらない。
公開の6項目を維持するか、対象ID等を追加するかは保存・UI担当者と合わせる。

## 6. 読み取りが増える場所

保存担当者のコードでは、検知追加の前後にget_sessionを呼び、
その中でdetections.stream()により既存の全検知文書を取り出す。

```text
record_detection：セッション＋既存の検知一覧を取得
  → add_detection：セッション確認、集計更新、新しい検知1件を保存
  → get_session：セッション＋更新後の検知一覧を取得して返す
```

60件を1件ずつ保存すると、追加処理だけで3781読取・120書込というコード上の見積り。
速度の実測によるボトルネック判定ではなく、読み取り量が増える原因の特定である。

保存側と確認する点：

1. 保存APIのレスポンスに全一覧が本当に必要か。
2. 保存API内で一覧取得が必要か。

確認した拡張側の呼出元は保存APIのレスポンスJSONを読み取っていない。
他の利用元にも依存がなければ、追加保存時は必要な通話情報だけを読み、集計と1件保存を行い、
保存したID・結果だけを返すか204とする。全一覧はレポート取得APIに寄せる。
集計と検知追加の同時更新・保存再送の重複防止も担当者と調整する。
他メンバーの保存コードは今回変更していない。

## 7. 分析状態管理の実測・概算

Emulatorで40発言を送った実測：

| 送信方式 | API回数 | 分析処理（mock） | 文書読取 | 文書書込 |
| --- | ---: | ---: | ---: | ---: |
| 新しい5件ごと | 8 | 8 | 16 | 16 |
| 1件増えるたびに累積配列 | 40 | 8 | 44 | 16 |

各方式で別途1読取し、分析済みID40件を検算した。表には検算分を含めない。
測ったのはSDKとEmulatorの実通信であり、請求レポートではない。AIは固定モック。
セッション保存・検知一覧取得の読み書きはこの表に含まない。

5件単位で60回分析するなら300発言で120読取・120書込。
月100通話なら分析状態管理のみ12000読取・12000書込（競合・再試行なしの換算）。
60「発言」なら12分析、24読取・24書込。60「分析」と区別する。

Firestoreの無料枠は日次であり、月間合計だけで無料を保証しない。
レポート保存等の全体見積りは [読み書き量の内訳](firestore-usage-estimate.md) を参照。

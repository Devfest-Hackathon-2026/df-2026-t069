# 開発ルール（Development Rules）

本ドキュメントでは、df-2026-waiwai-dev のチーム開発における共通ルールを定める。

## 1. 開発方針

- すべての変更は原則としてIssueを起点に行う。
- `main` と `develop` への直接pushは禁止する。
- 作業は個別のfeatureブランチで行い、Pull Request（PR）を通じて統合する。
- PRには最低1人の承認を必要とする。
- 秘密情報や個人情報をリポジトリにコミットしない。
- 他のメンバーの作業範囲に影響する変更は、事前に相談する。

## 2. ブランチ運用

### 2.1 ブランチの役割

| ブランチ | 役割 |
|---|---|
| `main` | デモ・発表用の安定版 |
| `develop` | 開発中の機能を統合するブランチ |
| `feature/#Issue番号-概要` | 新機能・タスクの作業ブランチ |

### 2.2 ブランチ作成

featureブランチは、最新の`develop`から作成する。

```bash
git switch develop
git pull origin develop
git switch -c 'feature/#12-audio-detection'
```

### 2.3 開発・マージの流れ

1. GitHubでIssueを作成する。
2. `develop`からfeatureブランチを作成する。
3. featureブランチで実装・テストを行う。
4. GitHubで`develop`宛てのPRを作成する。
5. 最低1人のレビュー承認を得る。
6. CI・テスト・競合の状態を確認してマージする。
7. デモ・発表用に安定した状態になったら、`develop`から`main`へPRを作成する。
8. `main`宛てのPRも最低1人の承認後にマージする。

### 2.4 ブランチ運用上の注意

- `main`と`develop`への直接pushは禁止する。
- 他のメンバーのfeatureブランチへ直接pushしない。
- 作業が完了したブランチは、マージ後に削除することを推奨する。
- ブランチ名にはIssue番号と作業内容を含める。
- 既存のブランチ名を変更する場合は、関係者と相談する。

## 3. Issue管理

- 原則として、実装・修正・調査などの作業にはIssueを作成する。
- Issueには目的、背景、作業内容、完了条件を記載する。
- 作業開始時に担当者を設定する。
- 関連するPRにはIssue番号を記載する。
- PRがIssueを完了させる場合は`Closes #Issue番号`を記載する。

## 4. Pull Request・レビュー

### 4.1 PR作成ルール

- PRのマージ先は通常`develop`とする。
- デモ・発表用の安定版を作成する場合は`main`をマージ先とする。
- PRテンプレートの項目を記入する。
- 関連Issueを明記する。
- 変更内容と影響範囲を具体的に説明する。
- 実施したテストと結果を記載する。
- UI変更の場合はスクリーンショットを添付する。

### 4.2 レビュールール

- マージには最低1人の承認を必要とする。
- PR作成者本人による承認はカウントしない。
- 指摘事項には対応し、必要に応じて修正後に再レビューを依頼する。
- 承認前にマージしない。
- CIが設定されている場合は、必須チェックの成功を確認する。

### 4.3 CODEOWNERS

`.github/CODEOWNERS`にディレクトリごとの担当ロールを記載する。

現在の`@role1-user`などは仮の名前であるため、実際のGitHub IDが確定した段階で置き換える。

## 5. ディレクトリ構成と担当範囲

| ディレクトリ | 主な担当 | 内容 |
|---|---|---|
| `frontend/` | Role1・Role2 | UI、画面、音声・映像取得、API連携 |
| `backend/` | Role3・Role4 | API、検知ロジック、設定、セキュリティ |
| `docs/` | Role4 | 設計書、API契約、ADR、開発資料 |
| `infra/` | Role4 | インフラ、デプロイ設定 |
| `samples/` | Role2 | デモ用サンプルデータ |
| `.github/` | Role4 | Issue・PRテンプレート、CI、CODEOWNERS |
| `.gemini/` | 共通 | Gemini関連の開発設定 |

- 原則として担当ディレクトリを中心に作業する。
- 他の担当範囲を変更する場合は、関係する担当者に事前相談する。
- 共通ファイルの変更は、影響を受けるメンバーと確認する。

## 6. API契約の変更

以下はfrontendとbackendの連携に関わる重要なファイルである。

- `frontend/src/types/`
- `backend/app/schemas/`
- `docs/api-contract.md`

これらを変更する場合は、次のルールを守る。

1. `docs/api-contract.md`も同時に更新する。
2. frontend・backend双方の担当者にレビューを依頼する。
3. リクエスト・レスポンスの形式、型、エラー形式を確認する。
4. 既存機能への影響を確認する。

## 7. コミットメッセージ

コミットメッセージは次の形式に統一する。

```text
<type>: <変更内容>
```

### type一覧

| type | 用途 |
|---|---|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメント変更 |
| `refactor` | リファクタリング |
| `test` | テストの追加・修正 |
| `chore` | その他の保守作業 |
| `ci` | CI/CDの設定変更 |
| `style` | 動作に影響しない書式変更 |
| `build` | ビルド・依存関係の変更 |
| `perf` | パフォーマンス改善 |

### コミット例

```bash
git add .
git commit -m "feat: 音声アップロード機能を追加"
git commit -m "fix: APIエラー処理を修正"
git commit -m "docs: 開発ルールを追加"
```

- 変更内容が分かる簡潔なメッセージにする。
- 1つのコミットには、できるだけ関連する変更をまとめる。
- 無関係な変更を1つのコミットに混在させない。

## 8. テスト・品質管理

- 実装した機能に応じたテストを実施する。
- backendはpytestによるテストを基本とする。
- frontendはlint・buildなどで品質を確認する。
- UI変更では表示・操作・レスポンシブ対応を確認する。
- PR作成前に不要なデバッグコードや一時ファイルを削除する。
- テストを実施できなかった場合は、その理由をPRに記載する。

## 9. 環境変数・秘密情報の管理

以下の情報は絶対にGitへコミットしない。

- APIキー、アクセストークン、パスワード
- `.env`などの環境変数ファイル
- Google Cloudサービスアカウント鍵
- 秘密鍵・証明書・認証情報ファイル
- 個人の音声・映像などのプライベートなメディア

### 環境変数の取り扱い

- `.env.example`には必要な変数名と説明を記載する。
- 実際の秘密情報は各自の`.env`で管理する。
- `.env`は`.gitignore`で除外する。
- 本番環境の秘密情報はGoogle Cloud Secret Managerなどで管理する。
- `NEXT_PUBLIC_`で始まる環境変数はブラウザに公開されるため、秘密情報を設定しない。

### デモ用メディア

- `samples/media/`のメディア本体は原則Git管理しない。
- 個人の声・顔などを含むデータは、本人の同意と適切なアクセス制御を確認する。
- 共有が必要な場合は、アクセス権限を制限した共有ストレージを利用する。

## 10. 秘密情報を誤ってコミットした場合

秘密情報を誤ってコミット・pushした場合、単にファイルを削除するだけでは不十分である。

以下の手順で対応する。

1. 直ちにチーム責任者へ報告する。
2. 該当するAPIキー・トークン・サービスアカウント鍵などを無効化する。
3. 新しい認証情報を発行し、利用箇所を更新する。
4. GitHub上の公開範囲やアクセス状況を確認する。
5. 必要に応じてGit履歴から秘密情報を除去する。
6. 関係者へ影響範囲と対応状況を共有する。
7. `.gitignore`などを修正し、再発を防止する。

**重要：** 一度GitHubへpushした秘密情報は、履歴から削除しても漏えいした可能性があるものとして扱う。最優先は認証情報の無効化・ローテーションである。

## 11. 開発時の基本確認

作業開始時：

```bash
git switch develop
git pull origin develop
git switch -c 'feature/#Issue番号-概要'
```

作業終了前：

```bash
git status
git diff --check
```

PR作成前：

- [ ] Issueの完了条件を満たしている
- [ ] 不要なファイルを含めていない
- [ ] 秘密情報を含めていない
- [ ] 必要なテストを実施している
- [ ] 関連ドキュメントを更新している
- [ ] PRテンプレートを記入している

---

本ルールはチームの開発状況に応じて見直し、変更する場合はPRを通じて合意を得る。

### 4.2 トークン数の仮定

公式トークン資料に基づく概算:

-   音声: 約32 tokens / 秒
-   動画（静的処理・デフォルト）: 約100 tokens / 秒（低解像度）、約300
    tokens / 秒（高解像度）。デフォルトは1 FPSのフレームサンプリング。
-   動画の100 / 300
    tokens毎秒は、フレームと音声を含む動画入力の概算として扱う。音声を別途加算して二重計上しない。
-   出力: 1リクエストあたり200 tokensと仮定する。実測値ではない。
-   プロンプト・contextの入力トークンは未計測のため計算から除外する。

実際の利用量はモデル、MIMEタイプ、解像度、フレームレート、プロンプト、応答内容で変わる。利用開始後はレスポンスのusage
metadataで実測する。

### 5.2 リクエストベース課金の単価と前提

Cloud Run公式料金表のリクエストベース課金の単価を用いる。

  項目                                                  単価
  ---------------------------- -----------------------------
  CPU（リクエスト処理中）           \$0.000024 / vCPU-second
  メモリ（リクエスト処理中）        \$0.0000025 / GiB-second
  リクエスト                     \$0.40 / 1,000,000 requests

試算前提:

-   Backend: 1 vCPU、1 GiB
-   1リクエストの処理時間: 1秒 / 3秒 / 5秒の3ケース
-   メディア送信1回につきBackendリクエスト1回
-   1リクエストあたりの処理中CPU・メモリを課金対象とする
-   最小インスタンス0を仮定
-   Frontendへのアクセス、ヘルスチェック、再試行、起動時の追加要素、通信料は除外

計算式:

`Backend compute cost = requests × processing seconds × (1 × CPU rate + 1 × memory rate)`

`Request cost = requests ÷ 1,000,000 × $0.40`

## 8. 合計費用の見方

### 8.1 現行実装

現行機能のGemini費用は非常に小さい。Backend Cloud
Run費用も、上記のリクエスト数・処理時間の仮定では少額であり、無料枠の残量に左右される。

現行機能で費用の中心になり得るのは、Gemini以外の未計上サービス、ネットワーク転送、ビルド・イメージ保管、ログ、Frontend稼働などである。これらは実際の利用量を確認して追加する。

### 8.2 将来の連続監視

将来の連続監視では、15分通話1回につき180回のGeminiリクエストが発生する。現時点の仮定では、Gemini出力を200
tokens /
requestと置いているため、出力料金が入力料金と同程度またはそれ以上になるケースがある。

特に高解像度動画では、映像入力tokensが増加する。実装時にはフレームレート・解像度・送信間隔を設計し、実測usage
metadataを使って見積もりを更新する。

## 9. 無料枠・クレジットの扱い

-   Gemini Developer API:
    料金表に無料枠が掲載されている。無料枠のデータ利用条件を確認し、医療・個人情報を含む可能性のあるデータでの利用可否をチームで判断する。
-   Cloud Run:
    リクエストベース課金の無料枠はCPU・メモリ・リクエスト数に月次上限がある。請求先アカウント内で他プロジェクトと共有される。
-   Speech-to-Text V1:
    標準モデルでは月60分無料の料金帯がある。対象方式・モデル・請求先アカウントの条件を確認する。
-   Firestore:
    Standardエディションには保存・読み書き等の無料枠がある。プロジェクトごとに1データベースのみ。
-   Google Cloud新規顧客向け無料クレジット:
    最大\$300の案内があるが、アカウント資格・期限・対象サービスの条件があるため、利用可能額として確定計上しない。

無料枠やクレジットは恒久的な単価引き下げではない。利用開始時にコンソール上の適用条件を確認する。

## 10. コスト削減案

1.  **映像フレームレートを制御する:**
    動画トークン数はサンプリングFPSに比例するため、必要な場面に絞ってフレームを送る。
2.  **解像度を抑える:**
    低解像度の動画入力は高解像度よりトークン数を抑えられる。
3.  **送信間隔を調整する:**
    5秒固定ではなく、リスク兆候やイベントに応じて送信頻度を変える。ただし検知性能・見逃し率を検証する。
4.  **音声・映像を必要なときだけ送る:**
    常時両方を送るのではなく、分析目的に応じてメディアを選択する。
5.  **プロンプトを短くする:**
    固定プロンプト・contextのトークン数を計測し、重複情報を減らす。
6.  **出力を必要最小限にする:**
    JSONスキーマと出力上限を設定し、不要な長文応答を避ける。
7.  **実測値で見積もりを更新する:** usage
    metadataを集計し、音声・映像・プロンプト・出力別の平均と最大値を確認する。
8.  **Cloud Runの最小インスタンスを増やさない:**
    コールドスタート要件と費用を比較し、必要性がなければ最小インスタンス0を維持する。
9.  **予算アラートを設定する:** Issue
    #2の予算アラートに本試算を反映し、実請求・予測請求を監視する。
